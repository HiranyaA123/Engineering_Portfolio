Project 01 of 06 / Hospitality software

CentralPass

I co-founded CentralPass and developed its direct ordering and venue operations software. The platform connects a branded customer website, payments, a live staff queue, owner tools and receipt printing. Built over several months, it is live at Caffe Primo Firle.

The problem

Give venues a direct connection to their customers.

CentralPass gives a venue its own branded ordering channel and connected operational tools. Customers order through the venue’s website, payments go into its Stripe account, and staff manage the order through preparation. The shared platform underneath includes the API, owner portal, staff dashboard and printer bridge.

My contribution

From customer checkout to the receipt printer.

I designed, implemented and deployed the application and its integrations over several months. My work spans the customer interface, backend data model, payments, staff tools and the local printer service.

  1. The storefront. A React and Vite site per venue, with menu browsing, modifiers, pickup ordering, checkout and bookings, built to the venue's brand rather than to a CentralPass look.
  2. The API and data model. Node and Express on PostgreSQL: menus, modifiers, orders, customers, offers, opening hours, venue settings and role based access, with schema migrations that run before every deploy.
  3. Payments. Stripe checkout with the payment confirmed server side by webhook before an order is allowed into the staff queue. The browser is never trusted to say that money arrived.
  4. The staff queue. A tablet first dashboard, packaged with Capacitor, that receives new orders over Socket.io, moves them through preparation and marks items sold out for every other screen in real time.
  5. The printer bridge. A small Node service that lives beside the thermal receipt printer at the counter, takes jobs from the hosted API and prints them, connecting the hosted order system to the venue’s printer. Outage recovery needs to be evaluated across the queue, network and printer together.
  6. The owner portal. Menus, hours, offers, customer records, reporting and time clock workflows, so the owner can run the venue without calling me.
  7. Per venue infrastructure. Each venue gets its own Railway project, database, R2 storage and configuration. Onboarding a new venue is a repeatable deployment, not a fork.

Engineering decisions

Designing for restaurant service.

  1. Use real-time events where latency matters. Socket.io pushes new orders, status changes and sold-out updates across customer, staff and owner interfaces.
  2. Keep uploads off ephemeral compute. Menu images stream to Cloudflare R2 instead of living on a Railway container that can be replaced.
  3. Migrate before every deploy. The production start path fails fast if the PostgreSQL schema cannot be updated safely.
  4. Protect venue ownership. Each client retains its domain and Stripe account, while credentials remain outside public front ends and source control.

Current scope

CentralPass is built and operating at its first venue. It covers direct ordering and payments, live staff order management, owner controls, customer and offer workflows, straightforward bookings, basic time clock workflows and receipt printing. Its scope is direct ordering and connected venue operations. It does not provide a complete POS, payroll, advanced rostering, marketplace customer acquisition or delivery logistics system.
